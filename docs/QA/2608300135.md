$$\text{World Manager (Outside)} = \text{Current worlds (Live memory instances and focus management)}$$

---

### Layer Responsibilities and Boundaries

#### 1. Inside Core (`src/core/`): What is a world
Core maintains **100% zero global instances and zero external state**, describing all spatiotemporal rules and entity contracts required to constitute a game world:
- Contracts (pure `interface` / `type`, zero internal imports).
- `abstract class device` (entity polymorphism base).
- `class space` (geometric space entity).
- Undo tree branching timeline pure algorithms.
- Reversible operation contracts.
- Law and item definition containers (`pack_registry`).
- Hook dispatch contracts.
- Top-level aggregation entity ($\text{World} = \text{Space} + \text{History} + \text{Registry}$).
- Public entrypoint `@/core`.

#### 2. Outside Core (`src/world.ts`): Live Instance Management (Current worlds, may > 1)
Holds live instances during application execution, managing world switching and scheduling:
- Multi-world instance repository (`pure_world` instances).
- Active world focus pointer.
- Multi-instance scheduling APIs (`create_world`, `get_active_world`, etc.).
- Partial-application shortcuts on the active world (`undo()`, `execute_command()`).

---

### Architectural Trade-off Evaluation (Balanced Advocacy)

#### Arguments in Favor
1. **Conceptual Clarity**:
   - Anyone wanting to understand "how a world operates" reads `src/core/`; anyone wanting to manage "parallel worlds" reads `src/world.ts`.
2. **Elimination of Reverse Dependencies**:
   - Layer 0 contracts require zero class imports, forming a clean unidirectional DAG.
3. **Unbounded Multi-World Capability**:
   - UI or CLI can connect to or switch between multiple independent worlds seamlessly, with fully isolated geometry and history trees.

#### Counterarguments & Costs
1. **Module Reorganization Overhead**:
   - Requires modular separation across `device.ts`, `space.ts`, `world.ts`, and `history.ts`.
2. **Naming Distinction**:
   - Requires distinguishing the world entity contract in Core from the active world manager in `@/world`.

---

Confirmed the architecture: **"Inside: What is a world (Core aggregation entity) + Outside: Current worlds (Multi-instance management center)"**, guiding subsequent Core refactoring and unidirectional DAG topology.
