## Questions and Answers

### Q1 · 2026-08-25 01:23 (human)
I don't quite understand why `API.ts` wraps things once more. Why can't they be wrapped directly inside `core`?

### A1 · 2026-08-25 01:24 (agent: gemini-3.7-flash)
There are two core architectural reasons:

1. **Preventing Circular Dependencies**:
   - Runtime instances (such as the active `global_history_tree`) live in `src/runtime.ts`.
   - `runtime.ts` needs to import constructors from `src/core/` (e.g., `create_history_tree()`) for initialization.
   - If `core` were to directly reference global instances, a circular dependency `core <-> runtime` would emerge.

2. **Preserving Core Purity and Multi-Instance Flexibility (Zero Global State)**:
   - `src/core/` remains pure algorithms and pure data structures (accepting `tree` / `map` explicitly as parameters), making unit testing straightforward and enabling sandbox branch rehearsals or multi-world scenarios without binding Core to singletons.
   - `src/API.ts` acts as a facade, binding the current runtime state and injecting it into Core pure functions, so callers (UI/CLI) enjoy convenient calls like `delete_node(3)` or `undo()` without manually passing instances around.

## Conclusion
`src/core/` focuses on pure mathematical structures and algorithms (zero global state); `src/API.ts` acts as a facade that injects runtime state, maintaining clear boundaries and eliminating circular dependencies.
