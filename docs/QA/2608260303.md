### Q1 · 2026-08-26 02:45 (human: wVQ88Soi2Il9)
History-related operations in the project are scattered across `core/history_manager.ts`, `runtime.ts`, and `packs/vanilla/history.ts`. How should their boundaries be clearly partitioned?

### A1 · 2026-08-26 02:45 (agent: claude-sonnet-5-mid)
The litmus test: **If this logic is removed, can the Undo Tree still correctly perform undo/redo/jump?**

- **Yes → Business semantics, belongs in `packs/vanilla` (stored in `other_info['vanilla']`)**:
  - Example: `pinned` markers—removing them leaves tree topology and navigation completely intact.
  - Example: `delete_branch`—removing it still leaves `delete_node` capable of achieving the same outcome (it is merely a composite wrapper around Core atomic operations).
- **No → Core algorithms, must stay in `src/core/`**:
  - Example: `find_lca`, `record_command`, `jump_to_node`.

`vanilla/history.ts` accessing runtime state is permitted—the "Core zero global state" rule strictly constrains `core/`, not `packs/`. The `other_info['vanilla']` namespaced extension mechanism (see QA 0002) is the established standard for Packs extending Core containers.

### Q2 · 2026-08-26 02:50 (human: wVQ88Soi2Il9)
What is the fundamental difference between `core` and `runtime`? If we remove runtime, where does state go?

### A2 · 2026-08-26 02:50 (agent: claude-sonnet-5-mid)
The litmus test: **Does this function's behavior change depending on which global `_map` / `_history_tree` is currently active?**

- **No (pure function, processes whatever parameters are supplied) → `core`**: e.g. `core.undo(tree, map)`.
- **Yes (only operates on the current active instance, fails without state) → `runtime`**: e.g. `runtime.undo()`.

**The essence of Runtime: curried global arguments**:
```ts
// Core signature:
core_undo: (tree: history_tree, map: game_map) => boolean

// Runtime partial application:
const undo = () => core_undo(GLOBAL_TREE, GLOBAL_MAP);
```
- **core** defines "what operations look like" (pure types and pure algorithms).
- **runtime** defines "which dataset operations target in this application" (injecting active instances).

Removing `runtime.ts` does not eliminate state; it merely scatters state access to `cli_tool` or forces artificial boilerplate parameter passing. `runtime.ts` encapsulates global instance ownership in a single place.

### Q3 · 2026-08-26 02:55 (human: wVQ88Soi2Il9)
What is the precise definition of "Core must not have state"?

### A3 · 2026-08-26 02:55 (agent: claude-sonnet-5-mid)
Distinguish two senses of State:
1. **Type / Shape of state (Definitions)**: Allowed and required in `core` (e.g. `interface game_map`, `interface history_tree`).
2. **Instances of state (Live memory data)**: Forbidden in `core` (Core must never hold `let _global_tree = ...`).

Core is stateless: its functions do not hold, rely on, or mutate self-owned instances; they operate strictly on passed-in arguments.

### Q4 · 2026-08-26 03:00 (human: wVQ88Soi2Il9)
What is the feasibility of multi-runtime instances? If Runtime is instantiated, what is the relationship with CLI and UI? Should we refactor now?

### A4 · 2026-08-26 03:00 (agent: claude-sonnet-5-mid)
1. **Multi-instance architectural evolution**:
   - Define `interface runtime_instance { map; registry; history_tree; }` (later `class pure_world`).
   - Functions accepting `runtime_instance` consolidate into `core` or `world`.
   - `runtime.ts` reduces to a minimal pointer tracking the active focus instance.
2. **CLI / UI relationship with multi-instances**:
   - CLI/UI does not need to be 1:1 bound to a single runtime.
   - **N UI/CLI instances can attach to the same runtime instance; a single UI/CLI operates on one runtime instance at any given moment**.
3. **Refactoring value**:
   - Clarifying boundaries between Core pure functions and curried global arguments proves Core's zero-global purity, sandbox capabilities, and streamlines runtime state.

## Conclusion

### Core Mental Model
1. **core**: Defines "what operations look like" (pure functions) + "what state looks like" (pure types). Never holds global instances.
2. **runtime**: Defines "which data operations target". Primarily acts as a parameter-binding forwarder.
3. **packs/vanilla**: Semantic business layer, extending generic containers via `other_info['vanilla']`.
4. **Multi-instances replace global currying**: Once multiple independent spaces/trees are supported, operations pass the instance explicitly to Core, and Runtime serves only as an active instance pointer.
