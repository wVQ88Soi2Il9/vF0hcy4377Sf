### Q2 · 2026-08-26 02:50（human: wVQ88Soi2Il9）
`core` 與 `runtime` 的本質區別是什麼？若不要 runtime，全域狀態會去哪？

### A2 · 2026-08-26 02:50（agent: claude-sonnet-5-mid）
判斷準則：**這個函式的行為，會不會因為「目前有哪個全域 `_map` / `_history_tree`」而不同？**

- **不會（純函式、給什麼參數處理什麼）→ `core`**：如 `core.undo(tree, map)`。
- **會（只認當前全域實例，無狀態則失敗）→ `runtime`**：如 `runtime.undo()`。

**Runtime 的本質：被 Curry 掉的全域參數（Global Args）**：
```ts
// core 給的原始函式：
core_undo: (tree: history_tree, map: game_map) => boolean

// runtime 做的事，等價於 partial application（偏函式應用）：
const undo = () => core_undo(GLOBAL_TREE, GLOBAL_MAP);
```
- **core** 定義「操作長什麼樣子」（純型別與純演算法）。
- **runtime** 決定「這個應用裡，操作永遠作用在哪一份資料上」（注入全域參數）。

若拿掉 `runtime.ts`，全域狀態不會消失，只會散落到 `cli_tool` 或被迫傳遞偽裝的顯式樣板參數。`runtime.ts` 是把「全域狀態持有權」收斂至單一檔案的最佳做法。

### Q3 · 2026-08-26 02:55（human: wVQ88Soi2Il9）
「Core 不該有 state」的精確定義是什麼？

### A3 · 2026-08-26 02:55（agent: claude-sonnet-5-mid）
必須將 State 拆成兩種意涵：
1. **State 的型別 / 形狀（定義）**：✅ 可以且必須在 `core`（如 `interface game_map`、`interface history_tree`）。
2. **State 的實例（記憶體中活著的資料）**：❌ 不可在 `core`（Core 不能寫 `let _global_tree = ...` 自己持有）。

Core 是無狀態的（Stateless）＝ Core 的函式不依賴、不修改任何自己持有的實例，只操作外部傳入的資料。

### Q4 · 2026-08-26 03:00（human: wVQ88Soi2Il9）
多 Runtime 實例的可行性如何？若將 Runtime 實例化，CLI 與 UI 的關係是什麼？要不要現在動手重構？

### A4 · 2026-08-26 03:00（agent: claude-sonnet-5-mid）
1. **多實例架構演進**：
   - 定義 `interface runtime_instance { map; registry; history_tree; }`。
   - 將吃 `runtime_instance` 參數的純函式收斂回 `core`。
   - `runtime.ts` 退化為「目前 Focus 在哪一個 instance」的極簡指標。
2. **CLI / UI 與多實例的關係**：
   - 不是每個 Runtime 都要綁死一套 CLI/UI。
   - **N 個 UI / CLI 可以連接到同一個 Runtime 實例；一個 UI/CLI 在某個時刻只操作一個 Runtime 實例**。
3. **動手重構的價值**：
   - 探索並顯式化「Core 純函式」與「Global Args Curry」的邊界，親眼驗證 Core 的零全域純度、多實例操作能力與 Runtime 的極簡化。

## 結論

### 核心心智模型（一句話收斂）
1. **core**：定義「操作長什麼樣子」（純函式）+「state 長什麼樣子」（純型別）。不持有任何全域實例。
2. **runtime**：決定「操作永遠作用在哪一份資料上」。本質是把 `(tree, map)` 全域參數 Curry 掉的無邏輯轉發捷徑。
3. **packs/vanilla**：業務語意層，透過 `other_info['vanilla']` 擴充通用容器。
4. **多實例與「Global Arg 的 Curry」互斥**：一旦支援多個獨立地圖/歷史樹，實例操作回歸 Core 純函式，Runtime 僅作為當前 Active Instance 的指標。
