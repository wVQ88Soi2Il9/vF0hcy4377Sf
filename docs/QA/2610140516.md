## 結論（草案，待確認）

> 工作名稱：**ledger**（待定，見待決 1）。以下所有名稱都可以改。

### 1. 目錄與檔案

```text
<root>/                       # 例：docs/ledger/
├── ledger.toml               # 設定：紀錄語言、時區
├── head.md                   # 自動產生，嚴禁手改
└── <YYYYMMDDHHMM>_<slug>.md  # 一個主題（thread）一個檔
```

- 檔名就是 thread id，不需要序號。同一分鐘、同一 slug 的重複由檢查器報出。
- 封存：換規格版本時，整批搬到 `<root>/archive/`，工具不讀。

### 2. 四種實體

| 實體 | 可變性 | 存的狀態 | 算出的狀態 |
|---|---|---|---|
| **Q 問題** | 內文可補充 | `dropped`（需人類來源） | `answered`：有 accepted 的 D 回答它；否則 `open` |
| **D 決定** | 不可變；要改就寫新的 D 取代 | `proposed` / `accepted` / `rejected`（後兩者需人類來源） | `superseded`：有 accepted 的 D 取代它 |
| **O 觀察** | 不可變 | — | — |
| **T 任務** | 正文可重寫，沿革只追加 | `todo` / `landed` / `accepted` / `rejected` / `handed-off` | `blocked`：`needs` 中有未到終態者 |

- **thread 本身不存 status**：有任何非終態實體就是 active，否則 closed。
- 原本的 `superseded` / `abandoned` 改由 D 表達：哪個決定取代或放棄了哪個方向。

### 3. 位址

```text
<thread>#<實體>        例：202610140516_ledger-spec#T3
```

實體編號在 thread 內依類型各自遞增（`Q1`、`D1`、`O1`、`T1`），不重用。
同一 thread 內也寫全位址；工具會檢查每一個引用。

### 4. 檔案文法

````markdown
# 202610140516_ledger-spec

- **prev:** `202610010900_old-topic` 或 —
- **spec:** ledger v1

## 主題

為什麼有這個主題，以及綁住所有實體的約束（≤ 20 行）。

## 條目

### Q1 · 2026-10-14 05:16:35+08:00 — 位址要不要用序號

內文。

### D1 · 2026-10-14 05:20:00+08:00 — 位址改用時間戳加 slug

- **state:** accepted
- **answers:** 202610140516_ledger-spec#Q1
- **source:** human: wVQ88Soi2Il9 · 2026-10-14 05:19 · 「都照你的建議」

決定內容與理由。

### O1 · 2026-10-14 05:30:00+08:00 — 61 份舊計畫從未使用「待決斷」

事實，然後推論。

### T1 · 2026-10-14 05:40:00+08:00 — 實作 check 指令

- **state:** landed
- **needs:** 202610140516_ledger-spec#T0
- **basis:** 202610140516_ledger-spec#O1、202610140516_ledger-spec#D1

正文：現在的完整內容。

**沿革**

- 2026-10-14 06:10 landed —— check 完成 → 202610140516_ledger-spec#O2
````

- 所有實體都帶建立時間戳，同一 thread 內由舊到新排列。
- 欄位一律寫成 `- **key:** value`；只有 T 有 `**沿革**`。
- D 與 O 寫入後不改。要更正，就寫一條新的 O；要改變決定，就寫一個 `supersedes` 舊 D 的新 D。

### 5. 權限矩陣

| 轉移 | agent 可直接寫 | 需要 `source: human…` |
|---|---|---|
| 建立 Q、O、T；建立 `proposed` 的 D | ✓ | |
| T：`todo` → `landed` | ✓ | |
| T：→ `accepted` / `rejected`；D：→ `accepted` / `rejected`；Q：→ `dropped` | | ✓ |
| T：→ `handed-off` | ✓（需指名目標） | |
| 拆分或合併 T | 提議 | ✓ |

`source` 的格式為：`human: <名字> · <時間> · 「<原話或連結>」`。

工具只檢查 `source` 是否存在、格式是否正確，無法驗證它的真實性。真實性屬於使用者能自行約束的範圍。

### 6. 只存一個方向的關係

| 存的 | 算出的 |
|---|---|
| `T.needs → T` | `blocks`、`blocked` |
| `T.basis → O/D` | 某個 O/D 被哪些 T 依賴 |
| `D.answers → Q` | Q 是否已 `answered` |
| `D.supersedes → D` | 舊 D 是否已 `superseded` |
| `T.handoff → T` | 承接自哪一格 |

### 7. 工具（單一 CLI，Python 標準函式庫）

| 指令 | 對象 | 作用 |
|---|---|---|
| `queue` | 人 | 等你的事：open 的 Q、proposed 的 D、landed 的 T |
| `index` | 兩者 | 重新產生 `head.md` |
| `show <addr> [--history]` | agent | 單一實體、它的依據、thread 的「主題」、相關的 D（含是否已被取代） |
| `check` | 兩者 | 一致性檢查；也能當 post-edit hook 使用 |
| `new <slug>` | agent | 建立 thread 檔與時間戳 |

檢查碼草案：

- **衝突**：`BAD_FORMAT`、`BAD_STATE`、`MISSING_SOURCE`、`DANGLING_REF`、`CYCLIC_NEEDS`、`DUPLICATE_THREAD`、`STAMP_OUT_OF_ORDER`、`BASIS_SUPERSEDED`（T 的 basis 引用了已被取代的 D）。
- **警告**：`OVERGROWN`、`HEADER_TOO_LONG`。

### 8. 給 agent 的指令片段（草案，貼進 AGENTS.md／CLAUDE.md）

```text
本 repo 用 ledger v1 記錄工作（docs/ledger/，規格見其 readme）。
- 開工前跑 `ledger queue` 與 `ledger index`；要做某一格就 `ledger show <addr>`，不要整份讀檔。
- 實作中發現的事寫成 O，然後繼續做；不要自行把發現變成 T。
- 不確定的事寫成 Q，等人回答；不要自己決定。
- T 做完設為 landed 並在沿革附上 → O；不得自行設為 accepted/rejected。
- 任何 accepted/rejected/dropped 都必須附上 `source: human: … 「原話」`。
- 每次寫入後跑 `ledger check`，有衝突就修，或回報給人。
```

### 10. 待決（請逐項確認）

每項依序寫出：選項、各自的代價、證據、做錯時改回的成本，最後才是建議。

#### 10.1 名稱

- **選項**：(a) 沿用 `ledger`；(b) 改用一個不和現有工具撞名的名字。
- **`ledger` 的優點**：會計帳本的語意正好就是這套規則 —— 已入帳的分錄不擦掉，更正要寫一筆新分錄，這和 D、O 不可變是同一件事。名字短，`ledger queue` 也好打。
- **`ledger` 的問題**：已經有一個知名的命令列記帳工具 Ledger（ledger-cli，純文字記帳），指令名稱就是 `ledger`；也有同名的硬體錢包品牌。在本 repo 裡用 `docs/ledger/` 沒有問題，但 P4 之後要獨立成工具時，指令名稱會在使用者的 PATH 上衝突，搜尋也找不到。
- **改回的成本**：P4 之前幾乎為零（只是目錄名與文件用字）；P4 之後很高，因為名稱會寫進每份紀錄的 `spec:` 欄、agent 片段，以及各個 repo 的設定。
- **建議**：P1–P3 先用 `ledger` 當工作名稱，**P4 之前必須換掉**。另開一個 Q 來追蹤，換名前先查套件庫與常見指令是否撞名。

#### 10.2 thread 不存 status，改由實體推導

- **選項**：(a) 存 status（v3／v4 的做法）；(b) 由實體推導：有任何非終態實體就是 active，否則 closed。
- **證據**：v3 的 16 個檢查碼裡，有 3 個（`DONE_WITH_OPEN_ITEMS`、`MISSING_REASON`、`SUPERSEDED_WITHOUT_SUCCESSOR`）的存在只是為了管住「存下來的 status 和實際格子狀態不一致」。也就是說，把 status 存起來，本身就製造了一類衝突，還得再寫檢查去抓它。另外 61 份 v3 計畫裡，`## 捨棄原因` 只出現過 1 次。
- **推導的代價**：
  1. 沒有「draft（還沒同意）」這個狀態。但它可以由 `proposed` 的 D 和 `todo` 的 T 表達 —— 還沒被接受的決定本來就是草案。
  2. 「放棄某個方向」要寫成一個 D（例如「不採用方案 X」），而不是改一個欄位。這多寫幾行，但放棄的理由本來就該被記下來。
  3. 只有 O 的 thread（純觀察紀錄）永遠是 closed。這是正確的：它什麼都不欠。
- **改回的成本**：低。之後如果真的需要 status，加一個欄位屬於新增，不破壞既有檔案。反過來，先存了再拿掉，就得清理所有舊檔。
- **建議**：(b)。

#### 10.3 D、O 不可變的檢查（`check --since <git ref>`）

- **它要防的事**：T 的 `basis` 指向 O 和 D。如果有人事後改了 O 的內文，等於回頭竄改證據，而所有依賴它的 T 都不會發現。這是紀錄系統最嚴重的一種失敗：紀錄在說謊。
- **做的代價**：
  1. 要決定比對哪一個 git ref（main 的 merge-base？上一次 check？），在本機、CI、雲端 session 各不相同。
  2. 修錯字也會被報出來，所以還得定義「允許的修改」，這會長出新的規則。
  3. 估計增加 50–80 行程式碼，外加一組測試。
- **證據**：目前能看到的 git 歷史裡，只有 14 個 commit 動過計畫檔，合計新增 2606 行、刪除 0 行，觀察標題從未被刪改。但大部分計畫是整批進入 git 的，在那之前是否被改過看不到，所以這個證據只能說明「最近沒有發生」，不能說明「從來沒有」。
- **不做的風險**：被改了也沒人知道。不過 git 本身保留了每一次修改，事後仍然查得到；缺的是「當下就被提醒」。
- **改回的成本**：低。之後再加是純新增。
- **建議**：v1 先不做，符合原則 4（沒有使用證據的機制不做）。P5 統計時用 `git log -p` 檢查 D、O 有沒有被改過；有，就在 v2 加上這項檢查。

#### 10.4 `source` 的格式：`human: <名字> · <時間> · 「<原話或連結>」`

- **三個部分各自的理由**：
  - **名字**：多人協作的 repo 需要知道是誰同意的。只寫 `human`（v3 的做法）無法分辨。
  - **時間**：讓讀者把它對回當時的對話或 PR；也讓「先同意、後反悔」這種情況可以排序。
  - **原話**：**這是最重要的一項。** 對話紀錄通常不會留下來（雲端 session 會被回收，聊天紀錄也不在 repo 裡），所以只有把原話寫進紀錄，日後的讀者才能自己判斷「這句話真的是同意嗎」。
- **其他選項與問題**：
  - 只放連結：聊天連結會失效，或者其他人沒有權限看。
  - 用人類的 commit 當作證明：要求人親手 commit，正好違反「人不親手寫入」的前提。
- **原話用原文，不翻譯**：你用英文打字，原話就照英文記。翻譯過的話已經不是來源本身。
- **代價**：每次終態轉移多一行。以 v3 的量來看是 108 次「完成」，也就是 108 行，可以接受。
- **限制**：工具無法驗證原話是不是真的。agent 若捏造原話，只能靠人在 `queue` 與 diff 裡發現，這屬於使用者能自行約束的範圍。
- **建議**：採用。

#### 10.5 尚未 commit 的 plan-history v4 怎麼處理

- **選項**：
  - (a) commit v4，當作 P4 之前的過渡層。
  - (b) 捨棄 v4，讓 `docs/history/` 回到 v3，等 P4。
  - (c) 兩者都不用，P4 之前暫停所有紀錄。
- **分析**：
  - P1 到 P4 之間仍會有程式碼變更，CLAUDE.md 要求記錄，所以 (c) 不可行。
  - (b) 的代價：之後每個 session 若要寫紀錄，agent 都得讀 619 行的 v3 規格；而 v4 是 248 行。只算這一項，就是每次多花數千 token。
  - (a) 的代價：短期內會同時存在三種格式（`archive/` 的 v3、v4、之後的 ledger），可能讓人混淆。不過 v4 目前只有 1 份計畫，P4 遷移時的成本接近零。
  - **v4 的工作有一半會被 ledger 沿用**：「舊資料搬進 archive、不再解析」正是 ledger P4 也要做的事，所以這次搬移不會白做。解析器的骨架、`head.md` 的呈現、只讀單格的工具，也都能在 ledger P2 中重用。
  - 依 CLAUDE.md 規則 7，過渡層必須寫明清除目標。
- **建議**：(a)。在 v4 的 readme 與 commit 訊息中寫明「過渡層，清除目標：ledger P4」。

#### 10.6 實體編號：依類型各自編號，或共用一個流水號

- **選項**：(a) 依類型各自編號（`Q1`、`D1`、`O1`、`T1`）；(b) 共用一個流水號（`#1`、`#2`、…，另外寫一個 type 欄位）。
- **(a) 的優點**：
  1. 只看位址就知道是哪一類。讀者看到 `basis: …#O3`，不用打開就知道它是事實。
  2. 工具可以只靠前綴檢查文法，例如「`basis` 只能指向 O 或 D」。即使目標檔案已經封存或不存在，這項檢查仍然成立。
  3. v3 的觀察本來就獨立編號（`O<n>`，和格子編號分開），61 份計畫裡沒有出過問題。
- **(b) 的優點**：編號直接反映建立的先後。但每個實體本來就有時間戳，這個資訊是重複的。
- **(a) 的代價**：要維護四個計數器。由 `new` 指令或 agent 讀取最大值來分配，負擔不大。另外，類型寫進了 id，所以 Q 不能「變成」D；但這本來就是對的 —— 回答問題的應該是一個新的 D，指向原本的 Q。
- **改回的成本**：高。位址一旦被引用就不能改，所以這一項最好現在就定。
- **建議**：(a)。
