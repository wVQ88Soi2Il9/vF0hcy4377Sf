## Questions and Answers

### Q1 · 2026-08-25 03:08 (human: wVQ88Soi2Il9)
I need to re-understand namespaces. How many forms do namespaces currently take? As far as I know, some things are exported as objects in `index.ts`, while others appear as strings. Isn't this somewhat confusing?

### A1 · 2026-08-25 03:09 (agent: gemini-3.7-flash)
Yes, earlier iterations suffered from conceptual confusion across different layers:
1. **Ambiguous `$` symbol**: Used both in directory hierarchies (`$basic_ui/` for extension directories) and in data structures (`$vanilla` as private property keys).
2. **Inconsistent `other_info` standards**: Some places used `$` sub-objects (`$vanilla: { pinned: true }`), while others flattened parameters (`{ device_uid, position }`), lacking unified boundaries.
3. **Unclear distinction between string IDs and exported objects**: Code module exports (TS objects) vs. global registry lookups (colon-delimited string IDs) lacked clear boundaries.

To resolve this ambiguity, standardized principles were established:
1. **Global resource / command IDs (String ID)**: Mandate `<pack_id>:<name>` format (e.g. `core:create_device`, `test:assembler`, `pipe:straight_pipe`) without exception.
2. **Dynamic entity extension bags (`other_info`)**: Generic open containers in Core (`device`, `history_node`, `map_command`) requiring Pack extensions must use their `<pack_id>` as the sub-object key (e.g., `node.other_info = { vanilla: { pinned: true, merged_from: 3 } }`), never flattened and without a `$` prefix.
3. **Cross-module extension directories**: The `$` symbol is strictly reserved for the filesystem (e.g., `src/packs/pipe/$basic_ui/`), never in runtime data structures.
4. **Pack module interface**: A Pack's public API is unified at its `index.ts` entrypoint.

### Q2 · 2026-08-25 03:12 (human: wVQ88Soi2Il9)
Why use strings for resource and command IDs instead of object structures?

### A2 · 2026-08-25 03:15 (agent: gemini-3.7-flash)
JavaScript lacks native value-based object hashing, so using objects as map keys requires custom hashing. A two-level Map registry (`Map<pack_id, Map<resource_id, T>>`) offers significant architectural advantages:
1. **Semantic clarity**: Provides a structured `namespaced_id` (`{ pack: string, id: string }`) interface, avoiding ad-hoc string splitting.
2. **Efficient Mod lifecycle management**: Unloading a pack (`unload_pack`) is an $O(1)$ delete on the child Map, without scanning global string keys.
3. **Interoperability**: The registry supports both structured `{ pack, id }` objects and `<pack>:<id>` colon strings; CLI and JSON serialization retain concise string formats.

## Conclusion
1. **Registry adopts a two-level Map structure** (`Map<pack_id, Map<resource_id, T>>`), enabling clean $O(1)$ pack unloading.
2. **Resources and definitions support structured `namespaced_id` objects** (`{ pack, id }`) while maintaining bidirectional compatibility with `<pack_id>:<name>` strings.
3. **`other_info` extension bags** mandate wrapping with `<pack_id>` keys without `$` prefixes.
4. **The `$` symbol** is strictly reserved for filesystem extension directories (`$<rely_pack>/`).
