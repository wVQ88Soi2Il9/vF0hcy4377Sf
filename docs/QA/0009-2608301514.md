## 提問與回答

### Q1 · 2026-08-30 13:XX（human）

`core_v3/definition_i.ts` 中目前的 hook 實作包含全域 `_subscribers`，並提供 `on_hook()`、`trigger_hook()`。

在 runtime instance architecture 下，Core 應該如何定義 hook？是否應該由 Core 建立 hook system，還是只定義 hook 的結構並交由下游自行構造？

### A1 · 2026-08-30 13:XX（agent: GPT-5.6 Sol）

Core 不應持有全域 subscriber state。

若 `definition_i.ts` 內直接存在：

```ts
const _subscribers = new Map(...);
```

則所有 runtime instance 都會共享同一份 hook state，與 runtime instance architecture 衝突。

Core 應只定義合法的 hook 資料結構；具體 hook registry 應由 runtime 或下游自行建立與持有。

因此應移除 Core 中的 singleton subscriber state，以及不必要的全域 `on_hook()` / `trigger_hook()` 實作。

### Q2 · 2026-08-30 13:XX（human）

Hook registry 希望採用 nested map，而不是將 namespace 與 hook ID encode 成單一字串。

### A2 · 2026-08-30 13:XX（agent: GPT-5.6 Sol）

Nested map 可以直接在資料結構中保留 namespace 層級，例如：

```ts
Map<
    namespace_id,
    Map<
        hook_id,
        ...
    >
>
```

相較於 `"namespace:hook_id"` 之類的 canonical string，這種設計不需要額外定義字串 encoding / decoding convention，也能清楚表達 namespace → hook 的階層關係。

### Q3 · 2026-08-30 13:XX（human）

是否需要另外定義 `hook_function`？

預期的 hook 使用方式很簡單：

1. 定義一個 functions array。
2. 下游主動把例如 `on_moving` 的 callback 掛入。
3. `on_moving` 發生時，依序 execute array 中所有 functions，並傳入事件資料。

### A3 · 2026-08-30 13:XX（agent: GPT-5.6 Sol）

若 Core 不需要額外描述 callback 的 metadata 或建立更強的 callback type contract，則沒有必要為 function 額外建立 `hook_function` abstraction。

最直接的形式可以是：

```ts
Array<(...args: any[]) => void>
```

也就是：

> 一個由 callback functions 組成的 array。

使用 Array 亦符合「依掛入順序執行 callbacks」的語意。

例如：

```ts
for (const hook of hooks)
{
    hook(other_info);
}
```

Core 可以只規定這個資料結構；如何掛入 callback、何時執行 callback，則由下游決定。

### Q4 · 2026-08-30 15:XX（human）

若型別寫成：

```ts
export const hooks: Record<string, Array<(...args: any[]) => void>> = {};
```

其中：

```ts
Array<(...args: any[]) => void>
```

確實表示 array of functions。

但為什麼 function return type 是 `void`，而不是 `any`？

### A4 · 2026-08-30 15:XX（agent: GPT-5.6 Sol）

`(...args: any[]) => void` 表示：

* `...args: any[]`：callback 可以接收任意數量、任意型別的參數。
* `void`：hook system 不使用 callback 的 return value。

這符合目前 hook 的用途：

```ts
for (const hook of hooks)
{
    hook(other_info);
}
```

hook 是 notification / side-effect mechanism；呼叫者只是通知所有 callbacks 某事件發生，而不收集 callback 的運算結果。

若改成：

```ts
(...args: any[]) => any
```

則表示 callback 的 return value 完全不受型別約束，呼叫端也可以取得一個 `any` result：

```ts
const result = hook(other_info);
```

因此 `any` 並不是 `void` 的單純「更通用版本」。

兩者表達不同 contract：

```text
void     = 呼叫端不使用 callback 的回傳值
boolean  = callback 應提供 true / false 判斷
T        = callback 應產生特定型別的結果
any      = 不檢查 callback 的回傳型別
```

如果未來某種 mechanism 需要 callback 的結果，例如：

```text
before_moving
    ├── callback A → true
    └── callback B → false
                    ↓
               cancel moving
```

則應明確定義其 return type，例如 `boolean`，而不是把所有 hook 改成 `any`。

## 結論

1. **Core 不持有全域 hook state。**
   `definition_i.ts` 只負責定義 hook 的合法資料結構；具體 registry 由 runtime / downstream instance 自行建立。

2. **Hook registry 採 nested structure。**
   Namespace 與 hook ID 保持獨立層級，不 encode 成單一字串。

   概念結構為：

   ```text
   namespace
   └── hook_id
       ├── callback
       ├── callback
       └── callback
   ```

3. **單一 hook event 的 subscribers 使用 Array。**
   基本 callback collection 為：

   ```ts
   Array<(...args: any[]) => void>
   ```

   Array 明確保留 insertion / execution order。

4. **目前不需要額外的 `hook_function` abstraction。**
   在沒有額外 metadata 或更強型別需求時，直接使用 function type 即可，避免不必要的 abstraction。

5. **Callback return type 使用 `void`。**
   Hook 目前定位為 notification / side-effect mechanism，呼叫者不應依賴 callback 的 return value。

6. **Core 不規定具體的 subscribe / trigger API。**
   下游可以自行掛入 callback：

   ```ts
   hooks.push(callback);
   ```

   並在事件發生時自行執行：

   ```ts
   for (const hook of hooks)
   {
       hook(other_info);
   }
   ```

最終原則為：

> Core 定義 hook 可以是什麼；runtime / downstream 決定有哪些 hook、掛入哪些 callbacks，以及何時觸發它們。
