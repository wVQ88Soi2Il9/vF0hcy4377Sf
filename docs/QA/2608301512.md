### Q1 · 2026-08-30 13:XX (human)

The hook implementation in `core_v3/definition_i.ts` contains a global `_subscribers` and exposes `on_hook()`, `trigger_hook()`.

Under the runtime instance architecture, how should Core define hooks? Should Core build the hook system, or merely define the hook structure and leave instantiation to downstream consumers?

### A1 · 2026-08-30 13:XX (agent: GPT-5.6 Sol)

Core should not own global subscriber state.

If `definition_i.ts` contains:

```ts
const _subscribers = new Map(...);
```

then all runtime instances will share the same hook state, violating the runtime instance architecture.

Core should only define valid hook data structures; concrete hook registries should be created and held by runtime or downstream instances.

Therefore, the singleton subscriber state and global `on_hook()` / `trigger_hook()` implementations in Core must be removed.

The hook registry should use nested maps rather than encoding the namespace and hook ID into a single string.

### A2 · 2026-08-30 13:XX (agent: GPT-5.6 Sol)

A nested map directly preserves the namespace hierarchy:

```ts
Map<
    namespace_id,
    Map<
        hook_id,
        ...
    >
>
```

Compared to canonical strings like `"namespace:hook_id"`, this design avoids arbitrary encoding/decoding conventions and cleanly represents the namespace → hook hierarchy.

### Q3 · 2026-08-30 13:XX (human)

Do we need to define a separate `hook_function` abstraction?

The intended usage is straightforward:
1. Define a functions array.
2. Downstream pushes callbacks (e.g. `on_moving`).
3. When `on_moving` occurs, execute all functions in the array sequentially, passing event payload.

### A3 · 2026-08-30 13:XX (agent: GPT-5.6 Sol)

If Core does not require extra callback metadata or a stricter contract, there is no need for a dedicated `hook_function` wrapper abstraction.

The most direct form is:

```ts
Array<(...args: any[]) => void>
```

Namely:
> An array composed of callback functions.

Using an Array naturally preserves the semantics of executing callbacks in registration order:

```ts
for (const hook of hooks)
{
    hook(other_info);
}
```

Core only specifies this structure; how callbacks are registered and when they are invoked is decided downstream.

### Q4 · 2026-08-30 15:XX (human)

If the type is written as:

```ts
Array<(...args: any[]) => void>
```

Why is the return type `void` rather than `any`?

### A4 · 2026-08-30 15:XX (agent: GPT-5.6 Sol)

`(...args: any[]) => void` specifies:
* `...args: any[]`: The callback can accept arbitrary arguments.
* `void`: The hook system ignores and discards any return value.

This matches the current purpose:

```ts
for (const hook of hooks)
{
    hook(other_info);
}
```

Hooks function as a notification/side-effect mechanism; callers notify callbacks that an event happened without gathering computed results.

If written as `(...args: any[]) => any`, callers could expect a return value:

```ts
const result = hook(other_info);
```

`any` is not merely a more general version of `void`; they express distinct contracts:

```text
void     = Caller ignores the return value
boolean  = Callback provides a true/false decision
T        = Callback produces a specific typed result
any      = Callback return type is unchecked
```

If a future mechanism requires callback results (e.g. interceptors/cancellation), define explicit return types (such as `boolean`) rather than defaulting to `any`.

## Conclusion

1. **Core does not hold global hook state.**
   `definition_i.ts` only defines the legal data structures for hooks; concrete registries are held by runtime/world instances.

2. **Hook registries use nested structures.**
   Namespaces and hook IDs maintain distinct levels:

   ```text
   namespace
   └── hook_id
       ├── callback
       ├── callback
       └── callback
   ```

3. **Subscribers for an event use Array.**
   The fundamental collection is:
   ```ts
   Array<(...args: any[]) => void>
   ```
   Arrays preserve insertion and execution order.

4. **No redundant `hook_function` abstraction.**
   Plain function types suffice without wrapper bloat.

5. **Callback return type is `void`.**
   Hooks are notifications; callers do not depend on callback return values.

The guiding principle:
> Core defines what hooks can be; runtime and downstream decide which hooks exist, which callbacks are attached, and when they fire.
