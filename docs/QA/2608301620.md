### Q1 · 2026-08-30 16:16 (agent: claude-sonnet-5-mid)
While refactoring `port` in `src/core_v3/definition_ii.ts`, an omission was noted: `space` uses a counter `next_device_uid: uid` to allocate `device_uid`, but what about `port.port_uid`? The interface only specifies the result (`port_uid: uid`), without defining where the number originates or who guarantees its uniqueness and stability across `get_port()` array re-ordering. Should `abstract class device` incorporate a counter like `next_port_uid`?

### A1 · 2026-08-30 16:18 (human: wVQ88Soi2Il9)
Using `next_device_uid` is merely an implementation choice to avoid duplicates. Do not conflate the essence of a `uid` with how it is allocated.

1. **Semantic contract of `uid`**: It only promises "a stable identifier to distinguish the same entity". Whether `device_uid` or `port_uid`, the contract itself does not mandate *how* uniqueness is guaranteed.
2. **`next_device_uid` is an implementation detail**, not part of the `uid` concept. It is one allocation strategy (incremental counter) chosen by `space`. Another container could use UUIDs, hashes, or external assignment to satisfy the same contract.

**Heuristic**: The contract layer (`interface` / `abstract class`) defines "what this is and what it promises"; how that promise is fulfilled is up to the concrete implementation and should never be pre-emptively constrained into the contract.

## Conclusion

1. `port.port_uid: uid` in `definition_ii.ts` only expresses the contract: stable within the device, unaffected by `get_port()` ordering, not a globally addressable key.
2. **Do not add any counter or allocation mechanism (such as `next_port_uid`) to `abstract class device` or `port` interfaces**. Stability guarantees are left to concrete device subclasses.
3. `space.next_device_uid` remains as an internal implementation detail of `space`, not a mandatory template for other UIDs.
