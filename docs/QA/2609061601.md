## Questions and Answers

### Q1 · (human: wVQ88Soi2Il9)
Can `get_command_describe` directly return `command?.other_info?.cli?.describe ?? ''`? Why was `unknown` chosen over `any` originally?

### A1 · (agent: gemini-3.8-flash-high)
1. In TypeScript, `unknown` is the top type ($\top$), enforcing type narrowing before access. Originally chosen in Core to isolate Pack metadata structures.
2. However, for dynamic metadata bags like `other_info`, `unknown` introduces accidental complexity, blocking natural optional chaining (`?.`) and nullish coalescing (`??`).
3. Switching `other_info` to `Record<string, any>` eliminates boilerplate assertions across packs without compromising runtime safety.
Decision: Adopted `Record<string, any>` across Core definitions.

### Q2 · (human: wVQ88Soi2Il9)
What happens if `rev_op.execute` is also aligned to `any`? Does `rev_op` only need (and should only have) `(sp: space)`?

### A2 · (agent: gemini-3.8-flash-high)
1. **Mathematical Invariant**: `rev_op` is an automorphism on space ($f: \mathcal{S} \to \mathcal{S}$). All operation parameters are fixed when instantiated in factory closures.
2. **Causal Replay Invariance**: During Undo/Redo, history traversal only has `(tree, sp)`. Trailing dynamic arguments cannot be replayed causally.
3. **Intent vs. Mutation**: `cmd` represents external intent `(...args: any[]): any`, while `rev_op` represents atomic in-space state mutation `(sp: space): void`.
Decision: Aligned `rev_op` to strictly `execute(sp: space): void; inverse(sp: space): void;`.

### Q3 · (human: wVQ88Soi2Il9)
The layered implementation became too verbose. What was unnecessary? Why must `parse_vector` and `parse_integer` be preserved?

### A3 · (agent: gemini-3.8-flash-high)
1. **Critical Correction**: `parse_vector` and `parse_integer` in `parser.ts` are not dead code; they are the CLI pack's public parsing primitives used by positional commands to validate space-delimited coordinates and integer UIDs. They must be preserved.
2. **Eliminated Accidental Complexity**:
   - Dropped the redundant `query.ts` file; in JavaScript/TypeScript, distinguishing `rev_op` from `cmd` at runtime requires only `'inverse' in target`.
   - Removed single-line wrapper functions (`execute_cmd`, `execute_rev_op`).
   - Consolidated `src/packs/cli` into 3 concise files (`parser.ts`, `help.ts`, `executor.ts`).

### Q4 · (human: wVQ88Soi2Il9)
Why pass `registry` or differentiate context as `world.pure_world | core.pack_registry`?

### A4 · (agent: gemini-3.8-flash-high)
1. **Runtime Context Ownership**: `pure_world` owns both `registry` and `space`. CLI is exclusively a runtime interaction tool; execution always occurs within a specific world.
2. **Zero Polymorphic Checks**: Directly accepting `target_world: world.pure_world` eliminates speculative type sniffing (`'registry' in context`, `'space' in context`). `target_world.registry` and `target_world.space` are guaranteed to exist.
3. **Automatic Lifecycle Wiring**: In `cli.world_init(target_world)`, the DevTools console (`globalThis.cli`) automatically binds to `target_world`.

## Conclusion
1. `core.rev_op` strictly accepts only `(sp: space): void`.
2. `src/packs/cli/parser.ts` preserves `tokenize_input`, `parse_argument`, `parse_vector`, and `parse_integer`.
3. `src/packs/cli/executor.ts` directly accepts `(input: string, target_world: world.pure_world)`, using `target_world.registry` and `target_world.space` without redundant parameter passing.
4. `src/packs/cli/index.ts` auto-binds console CLI in `world_init(target_world)`.
