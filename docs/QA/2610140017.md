- **status:** open
- **topic:** Pack 注入方式的風險盤點，以及從頭設計的精簡方案（manifest + 組裝期 patch + 單一 commit 事件）

## 提問與回答

### Q1 ·（human: wVQ88Soi2Il9）
整理目前 packs 注入方式的潛在風險。

### A1 ·（agent: claude）
盤點當時的實作（`src/main.ts`、`src/world.ts`、`src/packs/*/index.ts`），以臨時測試實際驗證部分項目：

- **`world_init` 從未執行（已驗證）。** `pure_world` 從 registry 中的 `pack_module` 呼叫 `world_init`，但 `vanilla_alpha.global_init` 註冊時沒有放入 `world_init`，因此 `device_change` / `history_change` 轉發鏈都沒有生效。根因是同時存在兩種「pack」：`main.ts` 的 module namespace（呼叫 `global_init`）與 registry 中的 `pack_module`（呼叫 `world_init`）。
- **trigger 期間退訂會跳過下一個 callback（已驗證）。** `for…of` 走訪即時陣列，而退訂使用 `splice`。
- **`main.ts` 建立的是 `pure_world`，不是 `std_world`**，因此目前入口不會產生 `vanilla_alpha` 的領域事件。
- **undo / redo / jump 不發 `device_change`**，jump 系列不發任何事件，觀察者會和實際狀態不同步。
- **由誰觸發 hook 尚未收斂**：QA `2608301803` 傾向由 operation 觸發，實作則由 `std_world` 的方法觸發；直接呼叫 `execute([op])` 時沒有領域事件。
- **callback 拋例外時，狀態只完成一半**：狀態與歷史已經寫入，後續通知卻中斷。
- **可重入沒有防護**；**事件順序與 payload 沒有明確契約**。
- **`world_init` 在建構子中執行**，這時子類別的欄位還沒初始化；**世界沒有銷毀流程**；**重複註冊時，退訂只移除第一筆**。
- **`pack_module.hooks` 的型別允許預先放入 callback**，但 `structuredClone` 遇到函式會拋出 `DataCloneError`（已驗證）。

### A2 ·（agent: claude）
從清單中移除測試一節，以及正常使用不會遇到的項目：hook 名稱打錯而被靜默吞掉、建立世界時沒傳 template、`current_hook` 被重新賦值、registry key 重複註冊。其餘項目保留。

### Q3 ·（human: wVQ88Soi2Il9）
如果整個重寫，你會有什麼辦法？

### A3 ·（agent: claude）
第一版提案仍以「修補眼下問題」為出發點：讓 `world_init` 成為 `pack_module` 的欄位，加入 `create_world` 工廠、事件佇列與 flush、每次注入各包一層唯一閉包以便精準退訂、trigger 時走訪快照，並在 `history.ts` 加入 `on_apply` 觀察參數，由 `std_world.commit` 統一發出事件。

### Q4 ·（human: wVQ88Soi2Il9）
從最初該怎麼設計開始，而不是為了解決眼下的問題。

### A4 ·（agent: claude）
改從需求出發。pack 和系統之間只有三種性質不同的關係：

| 需求 | 本質 | 生命週期 |
|---|---|---|
| 貢獻定義 | 宣告式資料 | 全域，組裝完成後不再改變 |
| 參與世界 | 行為 | 跟著每個世界 |
| 與他人溝通 | 契約 | 宣告是全域的，訂閱看情況 |

既有問題多半來自三者混在同一個機制裡。據此提出的原則：

1. pack 只負責描述，由宿主組裝（pack 不直接寫 registry）。
2. 全域的部分不可變，可變的部分屬於世界。
3. 順序由宣告決定（`requires` + 拓樸排序）。
4. 事件是對已提交狀態的陳述，由唯一的寫入路徑（commit）產生。
5. pack 拿到的是限定範圍的 context，宿主能追蹤訂閱、限制事件擁有權。
6. 事件傳遞語意第一天就定死：同步、提交後才發、FIFO、走訪快照、錯誤隔離、重入改為排入佇列。

並提出「每次提交只發一個 `committed(change_set)` 事件，細粒度事件只是過濾」作為核心取捨。

這一版仍保留了 install / disposer、限定範圍的 context、拓樸排序等機制，後面兩輪被逐步拿掉。

### Q5 ·（human: wVQ88Soi2Il9）
不會有 unload，還能再精簡。

### A5 ·（agent: claude）
沒有卸載之後，以下機制隨之消失：

- disposer、`dispose()`、按 pack 追蹤訂閱。
- **執行期動態訂閱。** 訂閱只在初始化時發生，可以直接寫在 manifest 的 `on` 裡。callback 是靜態函式，透過參數拿到 `world`。
  - 連帶消失的有：每個世界一份的 callback 表、`world_init`、template clone、`inject_hook`。
  - handler 表在組裝時建好並凍結，所有世界共用。
  - 隔離性靠「callback 只操作它收到的 world」保證，回到 QA `2608301803` 最初的想法。
- trigger 時走訪快照：表不會變，就不會一邊走訪一邊退訂。
- 限定範圍的 context、事件擁有權檢查、拓樸排序：pack 是固定集合，列表順序就是載入順序與 handler 執行順序。

每個世界需要的私有狀態，由 manifest 的 `create_state` 在建立世界時產生。

### Q6 ·（human: wVQ88Soi2Il9）
這樣要怎麼處理 patch？

### A6 ·（agent: claude）
agent 把 patch 理解為「一個 pack 修改另一個 pack 的定義或行為」。

catalog 組裝完就凍結，所以 patch 是組裝流程中的一個步驟，世界永遠只看得到 patch 之後的結果。

初版提案是 `patches: { kind, target, apply(prev) => next }[]`，附帶規則：目標必須存在、不能改變身分（`namespace` / `id`）、同一目標依 pack 順序串接、不允許刪除定義，以及「handler 是否可被 patch」的方案 A / B 二選一。

### Q7 ·（human: wVQ88Soi2Il9）
user 可以自行約束的問題不算問題。

### A7 ·（agent: claude）
依此原則，用規範就能約束的事項不再以機制防範。

**patch 收斂為單一函式 `patch(draft)`**，直接修改尚未凍結的 catalog：
- 改欄位、替換、包裝、刪除定義都直接在 draft 上做。
- 改別人的 handler 時，透過對方匯出的函式參照，在 `draft.handlers` 中過濾或替換，不需要另外命名。
- 上一輪的檢查規則、`kind`、方案 A / B 全部移除。

**事件傳遞也一併收斂：**
- callback 拋錯時不收集、不包裝，例外照常往外丟。
- 不設重入佇列：handler 中呼叫 `submit` 就同步巢狀執行，是否形成循環由使用者自行約束。
- `emit` 只剩一個依序呼叫 handler 的 `for` 迴圈。

## 結論（待確認）

> 以下為提案，尚未經 human 確認，也尚未實作。

### 1. Pack manifest

```ts
interface pack_manifest
{
    pack_id:       string;
    provides?:     { items?, recipes?, devices?, operations?, commands? };
    on?:           Record<string, hook_callback>;   // 'ns:id' → handler(world, ...args)
    create_state?: () => unknown;                   // 這個 pack 在每個世界的私有狀態
    patch?:        (draft: catalog) => void;        // 組裝期間修改尚未凍結的 catalog
}
```

### 2. 組裝（全域，一次）

```text
compose(manifests):
  1. 依 ENABLED_PACKS 順序合併所有 provides 與 on，得到 draft
     （handlers: Map<namespace, Map<id, hook_callback[]>>）
  2. 依相同順序呼叫每個 pack 的 patch(draft)
  3. 凍結 draft → catalog
```

### 3. 世界（每個世界一份）

```text
create_world(catalog, space) → { space, history, pack_state: Map<pack_id, unknown> }
```

### 4. 唯一寫入路徑

```text
submit / undo / redo / jump
  → commit：透過 history.ts 套用 op，收集 change_set
  → 依序呼叫 core:committed 的 handlers(world, change_set)
```

- 每次提交只發一個事實事件。細粒度事件（例如 `create_device`）可以當作過濾的語法糖，是否提供尚未決定。
- `history.ts` 仍然是純演算法，不認識 hook。要如何回報套用過的 op（觀察參數，或是回傳值），尚未決定。
- `rev_op` 仍然只操作 `space`（延續 QA `2609060237`）。

### 5. 保留的既有決策

- core 只定義 hook 可以是什麼，由 runtime 決定實際有哪些 hook、何時觸發（延續 QA `2608301512`）。
- 訂閱以 callback 陣列保存，允許重複、保留順序；回傳值為 `void`。

### 6. 需 human 確認的分歧

1. **推翻 `src/README.md` 的不變式。** 原本是「Hook callbacks are per-world」，改為「handler 是全域且不可變的，世界透過參數傳入」。原本的目的「A 世界的 callback 不影響 B 世界」仍然成立。
2. **是否真的沒有執行期才附加的觀察者？** 例如 UI 打開某個世界的視圖時才開始監聽。如果有，需要保留一個極小的每世界 `on()`，只能新增，不能移除。
3. **由 commit 統一發出事件。** 不採用 QA `2608301803`「由 operation 觸發 hook」的方向。
4. **移除 `global_init` 這個概念。** `pack_module` 從「registry 條目」改為「交給 compose 的 manifest」。
5. **每次提交只發 `committed(change_set)`。** 細粒度事件是否以語法糖提供，由你決定。

### 7. 刻意保持未決

- 型別化的 payload。
- 存檔後更換 pack 組合時的版本相容性（patch 過的 operation 與既有歷史的關係）。
