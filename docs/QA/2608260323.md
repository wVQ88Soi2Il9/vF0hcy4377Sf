#### 1. `runtime` → `world`: Domain Model Alignment
- `runtime` is low-level CS jargon emphasizing execution phases; `world` is the core domain entity for simulation and game systems.
- A **`world`** encapsulates:
  - **`space` (geometric space)**: Multi-dimensional coordinates, spatial hashing, device layout.
  - **`history_tree` (temporal history)**: Branching timelines, Undo/Redo, state snapshots.
  - **`registry` (laws & entities)**: Item definitions, recipes, device constructors.
- Concepts like "Switch World" or "Parallel Worlds" are much more natural than "Switching runtime instance".

---

#### 2. `map` → `space`: Mathematical Alignment and Avoiding JS Keyword Collisions
- **Avoiding JavaScript keyword confusion**:
  - JS has built-in `Map` and `array.map()`, causing constant visual confusion between `new Map<number, device>()` and `map: game_map`.
- **Mathematical essence**:
  - The project supports arbitrary dimensions ($N$-D), hypercube geometry, spatial hashing, and hyperplane slice projections.
  - Mathematically, this discrete coordinate grid is a Vector/Grid Space. Calling it `space` aligns with mathematical reality.
- **The Trinity Model**:
  $$\text{World} = \text{Space} + \text{History} + \text{Registry}$$

### A2 · 2026-08-26 03:35 (agent: gemini-3.7-flash-high)

Bidirectional architectural evaluation of `class world`:

#### Arguments in Favor (Why we should)
1. **High Cohesion & Ergonomics**:
   - Clean caller semantics: `world.execute(cmd)`, `world.undo()`, `world.redo()`, `world.jump_to(uid)`.
   - `world` encapsulates its own `space`, `history`, and `registry`, preventing accidental cross-world mismatches (passing World A's history tree to World B's space).
2. **Clean Multi-Instance Isolation**:
   - Instantiating a new world is simply `const w = new world(...)`, each holding isolated state and camera focus without hidden module-level singletons.
3. **OOP Polymorphism & Extension**:
   - Enables future specialization via inheritance or composition (e.g. `readonly_world`, `simulation_world`, `diff_world`).
4. **Consistency with `abstract class device`**:
   - Aligns the entity tier with an object-oriented paradigm across both device and world levels.

---

#### Counterarguments & Trade-offs (Why we shouldn't)
1. **Purity of Core Algorithms**:
   - Embedding Undo Tree replay (`find_lca`, `jump_to_node`) directly into `class world` risks coupling pure algorithms to instance state (`this.space` implicit mutations), making pure algorithm unit tests harder.
2. **Serialization Overhead**:
   - Plain data objects (POJOs/interfaces) serialize directly via `JSON.stringify`, whereas classes with methods require explicit `serialize()` / `deserialize()` schemas for snapshots and Web Workers.
3. **`this` Binding Traps in Callbacks**:
   - Passing methods like `world.undo` as UI or CLI event callbacks risks runtime `undefined` without explicit arrow binding or autobinding.
4. **Reverse Dependency Risk in Commands**:
   - Reversible operations (`space_command`) should only depend on geometric `space` (`execute(space)`, `inverse(space)`). Binding operations to the entire `world` violates atomicity.

### A3 · 2026-08-26 03:56 (agent: gemini-3.7-flash-high)

Bidirectional evaluation of refactoring `space` from an interface into `class space`:

#### Arguments in Favor
1. **State Encapsulation**:
   - Dimensions, size, UID generators, and device lists are encapsulated, providing clean methods like `sp.create_device(...)`.
2. **Hook Trigger Reliability**:
   - Mutation hooks trigger inside `class space` methods, preventing external code from mutating devices while bypassing hooks.
3. **Unified OOP Hierarchy**:
   - Produces a coherent domain tier: `world (class)` $\rightarrow$ `space (class)` $\rightarrow$ `device (class)`.

#### Counterarguments & Trade-offs
1. **Snapshot Overhead**: Deep-cloning requires serialization/deserialization rather than shallow copying.
2. **Pure Function Compatibility**: Requires thin forwarding wrappers in `space_manager.ts` to support functional styles.
