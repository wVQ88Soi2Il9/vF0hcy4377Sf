**Q: Should hooks belong to each world instance?**

A: Not necessarily.

The hook registry acts as a static definition mapping a hook to its callback sequence:

```ts
Map<hook_id, callback[]>
```

Using an `Array` is deliberate: callback ordering and repetition may carry semantic significance, allowing:

```text
func_a → func_b → func_a
```

If downstream requires unique callbacks, it can enforce that locally; Core definition should not artificially force a `Set`.

---

**Q: With multiple worlds existing simultaneously, won't static hooks collide?**

A: No. `world` should be passed as an argument to the callback, rather than becoming part of the hook registry.

Conceptually:

```ts
trigger_hook('device:moved', world_a);
```

is equivalent to:

```ts
func_a(world_a);
func_b(world_a);
func_a(world_a);
```

Thus the callback operates on the world passed to this trigger call, avoiding the need for every world to hold a duplicate hook definition.

---

**Q: Who should trigger the hook?**

A: In principle, the operation performing the state transition should trigger the corresponding hook:

```text
move_device.execute(world)
    → mutate world
    → trigger device:moved(world)
```

This guarantees consistent events regardless of whether the operation was initiated by UI, CLI, history replay, or another entrypoint.

If history's internal state changes, it can trigger history-specific hooks separately:

```text
operation.inverse(world)
    → domain hook

history cursor changed
    → history hook
```

Both describe different layers of events and do not conflict.

---

**Q: Should reversible_operation operate on space or world?**

A: If operations are responsible for triggering hooks, operating on `world` should be considered.

Previously:

```ts
execute(space): void;
inverse(space): void;
```

Alternative:

```ts
execute(world): void;
inverse(world): void;
```

Because `world` represents the complete runtime instance/context; operations perform state transitions on that world and pass it along to associated hook callbacks.
